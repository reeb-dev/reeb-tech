API de ARCA para developers

Cómo hacer que un sistema de stock single-tenant pueda pedir un CAE (factura electrónica) hablando con ARCA/AFIP: primero te autenticás (WSAA), después autorizás el comprobante (WSFEv1).

SOAP/XML · no REST RG 4291 · V.4.8 RG 5616 PDFs oficiales
Empezar en 5 min Ver gaps actuales Fuentes oficiales
Para quién es. Backend (Java/Spring u otro stack) que implementa o revisa la integración. No es asesoría fiscal ni lista de precios. Si el PDF oficial dice otra cosa, gana el PDF.

Si solo tenés 5 minutos

  1. No hay API REST de ARCA. Es SOAP/XML por HTTPS. Vos firmás un XML, mandás un CMS, recibís un ticket, y con ese ticket pedís el CAE.
  2. Sin el certificado del CUIT del comercio (asociado al WSN wsfe) no arranca nada. REEB no “presta” certificado.
  3. Dos pasos siempre: WSAA te da token+sign (~12 h) → WSFEv1 usa eso en cada request.
  4. Hoy el gap crítico es no enviar CondicionIVAReceptorId (RG 5616): puede rechazar el CAE. Ver gaps.

Modelo mental (antes de mirar XML)

Pensalo como tres capas. Si mezclás ambientes (homo/prod) o pedís TA de más, fallás antes de llegar al CAE.

Capa 1 Identidad del comercio

CUIT + certificado X.509 + clave privada + punto de venta electrónico. Vive solo en el servidor.

Capa 2 WSAA = “login”

Firmás un TRA, llamás loginCms, cacheás el TA. Sin TA válido, WSFE ni te mira.

Capa 3 WSFEv1 = “autorizar factura”

Consultás el último número, armás el comprobante, pedís CAE, guardás resultado.

Camino de punta a punta

  1. Homologación del cliente CUIT + certificado + asociación al WSN wsfe + PV electrónico. Sin esto, cualquier código “correcto” igual falla.
  2. WSAA → Ticket de acceso (TA) Firmar TRA (CMS), loginCms, cachear token + sign (~12 h). Reutilizá el TA; no pidas uno nuevo en cada factura.
  3. WSFEv1 → número + CAE FECompUltimoAutorizado → FECAESolicitar → persistir CAE / vencimiento. El número siguiente sale del último autorizado, no lo inventés.
  4. Cerrar gaps de producto Sobre todo CondicionIVAReceptorId y DocTipo/DocNro reales. Ver tabla de gaps antes de pasar a producción.

Glosario (sin vueltas)

WSAAServicio de autenticación. Te entrega el Ticket de Acceso.
TRAXML LoginTicketRequest que firmás (CMS) y mandás a WSAA.
TAtoken + sign (~12 h). Van en el bloque Auth de cada WSFE.
WSFEv1Facturación electrónica con CAE (sin detalle de ítem en el XML).
CAECódigo de autorización + fecha de vencimiento. Es lo que “habilita” la factura.
Homo / ProdDos mundos. Certificados y URLs no se cruzan. Nunca uses cert de homo en prod.

1. Alcance del producto

Esto es lo que el piloto contempla hoy. Si el cliente necesita otra cosa (exportación, detalle de ítem, contingencia), se cotiza aparte.

Incluido en el piloto Fuera de alcance por defecto
WSFEv1 CAE (RG 4291) — comprobantes A/B/C sin detalle de ítem WSFEX, WSCT, WSMTXCA, WSBFE, WSSEG
WSAA LoginCms + TA cacheado CAEA (contingencia) salvo cotización
Persistencia CAE / vencimiento en la venta Libro diario / DDJJ
Transporte. SOAP/XML sobre HTTPS hacia ARCA. No existe un endpoint JSON “oficial” de facturación para este flujo.

Secuencia al emitir un CAE

1
Certificado del comercio Paths a cert + key en el servidor (env). CUIT del titular del cert.
2
WSAA LoginCms TRA firmado CMS (SHA1+RSA), Base64 → TA (token + sign).
3
WSFE FECompUltimoAutorizado Último nro por PtoVta + CbteTipo → calculás el siguiente.
4
WSFE FECAESolicitar Resultado A/R + CAE + CAEFchVto (+ observaciones/errores).
5
Persistir arca_invoice + campos CAE de la venta. No re-solicitar si ya hay A.

2. Checklist del cliente (bloqueante)

Marcá esto con el comercio / contador antes de pelear contra el SOAP. Si falta un ítem, el código no va a “arreglarlo”.

  • CUIT activo y situación fiscal definida con su contador.
  • Clave fiscal operativa.
  • Certificado digital del ambiente correcto:
    • Homo: WSASS (manual, adhesión).
    • Prod: Admin. de Certificados + obtener / asociar WSN.
  • Certificado asociado al WSN Facturación Electrónica (wsfe).
  • Punto(s) de venta electrónicos habilitados (el mismo que vas a poner en ARCA_PTO_VTA).
  • Reloj del servidor sincronizado (NTP; el manual cita time.afip.gov.ar, zona GMT-3).
  • Cert + clave solo en el servidor (paths en secrets). Nunca en git ni en el front.
Sin certificado + asociación WSFE no hay integración posible. El producto no presta un certificado de REEB a terceros.

3. WSAA — el “login”

Objetivo: obtener un TA usable. Fuentes: Especificación técnica · Manual Dev (oficial en fuentes).

Pasos (en orden)

  1. Armar LoginTicketRequest (TRA): uniqueId, generationTime, expirationTime, service=wsfe.
    • source / destination son opcionales; el FAQ recomienda omitirlos.
  2. Firmar CMS SignedData (SHA1+RSA) con cert + clave privada.
  3. Codificar el CMS en Base64.
  4. Invocar loginCms / LoginCms.
  5. Extraer token + sign; respetar expirationTime (~12 h). Reutilizar el TA vigente.

Cuando falla el login (lo más común)

Qué ves Causa típica Qué hacer
Cert no emitido por AC de confianza Cert homo en prod (o al revés) Usar el cert del ambiente correcto
Computador no autorizado a servicios / al servicio Cert sin asociar a WSN, o service mal WSASS (homo) o Admin Relaciones (prod); service=wsfe
CEE ya posee un TA válido Pediste TA de nuevo demasiado pronto Cachear TA; no re-login mientras viva
generationTime / expirationTime inválidos Reloj desfasado o formato NTP; restar unos minutos a generationTime
Firma inválida / CMS bad PEM mal, ambiente cruzado Revisar firma, encoding y paths

Retención al pedir TA de más (FAQ): ~10 min testing / ~2 min prod (puede cambiar). URLs en Fuentes oficiales. Defaults en código: wsaahomo.afip.gov.ar / wsaa.afip.gov.ar.

4. WSFEv1 — pedir el CAE

Manual principal: WSFEv1 RG 4291 V. 4.8 (copia local; oficial en homologación externa).

Auth en cada request

El TA de WSAA viaja así en el SOAP:

Auth (cada WSFE)XML
<Auth>
  <Token>…</Token>
  <Sign>…</Sign>
  <Cuit>…</Cuit>   <!-- CUIT representado -->
</Auth>

Errores de infra del manual: 600 token/firma · 601 CUIT no en token · 500/501/502 internos.

Métodos que vas a tocar

MétodoPara qué sirve

CAEA (FECAEA*) queda fuera del piloto salvo cotización.

FECAESolicitar — qué no puede faltar

Cabecera: CantReg, PtoVta, CbteTipo. En el detalle (FECAEDetRequest), entre otros:

  • Concepto — 1 productos / 2 servicios / 3 ambos
  • DocTipo / DocNro — documento del receptor
  • CbteDesde / CbteHasta / CbteFch — fecha en yyyyMMdd
  • Importes: ImpTotal, ImpTotConc, ImpNeto, ImpOpEx, ImpTrib, ImpIVA
  • MonId (PES) / MonCotiz
  • Iva → AlicIva (Id, BaseImp, Importe) — no informar en tipo C (según manual)
  • CondicionIVAReceptorId — ver abajo

Resultados: aprobado · aprobado con observaciones · rechazado. Persistí CAE, CAEFchVto, Resultado y errores/obs.

4.1 CondicionIVAReceptorId (RG 5616)

  • Campo agregado junto con CanMisMonExt.
  • Con obligatoriedad RG 5616, emitir sin el dato rechaza.
  • Valores vivos: FEParamGetCondicionIvaReceptor.
Gap actual en stock-local: el cliente WSFE aún no envía CondicionIVAReceptorId. Prioridad A2 — ver tabla.

4.2 Alícuotas (ejemplos del manual)

En ejemplos SOAP: Id=5 → 21 % · Id=4 → 10,5 % · Id=3 → 0 % · Id=6 → 27 %.
Catálogo vivo: FEParamGetTiposIva (no hardcodear en prod).

7. Gaps vs manual (prioridad A2)

Cosas que el manual / la RG ya exigen o conviene cerrar antes de prod. Empezá por las de riesgo alto.

GapRiesgoAcción
No envía CondicionIVAReceptorId Alto rechazo RG 5616 Mapear condición fiscal → id; usar FEParamGetCondicionIvaReceptor
Solo DocTipo 99 / DocNro 0 Alto no factura a RI con CUIT Usar DocTipo/DocNro del cliente de la venta
AlicIva fija Id=5 Medio mal con 10,5 / 27 / exento Mapear alícuota → Id; multi-alícuota

Sin tests automatizados Medio regresiones Unit mapeos + WireMock SOAP
XML SOAP en DB Bajo retención / acceso Restringir roles; no exponer al front

8. Seguridad

  • Cert/key fuera de git (*.pem, paths en secrets del VPS).
  • Solo TITULAR solicita CAE.
  • No devolver stack traces ni XML crudo al browser.
  • HTTPS obligatorio en prod.
  • Un certificado = un CUIT del cliente; nunca un cert “de REEB” para terceros (hosted).

10. Orden de trabajo recomendado

  1. Completar checklist del cliente (homo).
  2. Cerrar gaps §7 (empezar por CondicionIVAReceptorId + DocTipo real).
  3. UI panel: estado ARCA + “Solicitar CAE” + errores legibles.
  4. Ticket / impresión con CAE.
  5. Solo entonces PROD.

Relación con hosted / piloto

En el plan mensual cada suscriptor aporta su CUIT y certificado (o alta asistida cotizada). Una instancia = un comercio; no hay certificado compartido multi-tenant.
