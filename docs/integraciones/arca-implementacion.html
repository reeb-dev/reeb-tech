Receta: hacerla andar en tu API

Seguí este orden. Si saltás un paso, el siguiente falla.

1

Homologá el CUIT del comercio

Certificado + asociación al WSN wsfe + punto de venta electrónico. Sin esto no hay login.

2

Implementá WSAA loginCms

Armá el TRA → firmá CMS (SHA1+RSA) → Base64 → SOAP → cacheá token + sign (~12 h).

3

Implementá WSFEv1

FECompUltimoAutorizado → calculá nro siguiente → FECAESolicitar → leé CAE / Resultado.

4

(Opcional) Exponé tu REST

Ej.: POST /api/arca/invoices/{saleId} que adentro hace los pasos 2–3. Ver colección Postman.

5

Probá en HOMO hasta un CAE A

Incluí CondicionIVAReceptorId (RG 5616). Recién después pensá PROD.

Prerrequisitos (bloqueantes)

  • CUIT + clave fiscal del comercio
  • Certificado del ambiente (homo ≠ prod)
  • Cert asociado a Facturación Electrónica (wsfe)
  • Punto de venta electrónico habilitado
  • Reloj del servidor sincronizado (NTP / GMT-3)
  • Cert + clave privada solo en el servidor

Webservice 1 — WSAA (autenticación)

Objetivo: obtener el Ticket de Acceso (token + sign) para usar en cada llamada WSFE.

SOAP loginCms WSAA
Content-Type: text/xml service = wsfe CMS SHA1withRSA

Paso A — LoginTicketRequest (TRA)

XML a firmarTRA
<?xml version="1.0" encoding="UTF-8"?>
<loginTicketRequest version="1.0">
  <header>
    <uniqueId>1710000000</uniqueId>
    <generationTime>2026-09-23T21:55:00-03:00</generationTime>
    <expirationTime>2026-09-24T08:00:00-03:00</expirationTime>
  </header>
  <service>wsfe</service>
</loginTicketRequest>

source/destination son opcionales (el FAQ recomienda omitirlos). Restá unos minutos a generationTime si el reloj falla.

Paso B — Firmar y llamar

  1. Firmá el TRA como CMS SignedData (SHA1+RSA) con cert + clave del comercio.
  2. Codificá el CMS en Base64.
  3. Enviá SOAP loginCms con ese Base64.
  4. Parseá <token> y <sign>. Cacheá ~11–12 h. No pidas TA en cada factura.
SOAP request (esqueleto)WSAA
<soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/"
  xmlns:wsaa="http://wsaa.view.sua.dvadac.ubaar">
  <soapenv:Header/>
  <soapenv:Body>
    <wsaa:loginCms>
      <wsaa:in0>BASE64_DEL_CMS…</wsaa:in0>
    </wsaa:loginCms>
  </soapenv:Body>
</soapenv:Envelope>

Webservice 2 — WSFEv1 · último número

SOAP FECompUltimoAutorizado WSFEv1
SOAPAction: http://ar.gov.afip.dif.FEV1/FECompUltimoAutorizado

Devuelve el último comprobante autorizado para ese PtoVta + CbteTipo. El siguiente es último + 1.

Body (dentro del Envelope)ejemplo
<FECompUltimoAutorizado xmlns="http://ar.gov.afip.dif.FEV1/">
  <Auth>
    <Token>…</Token>
    <Sign>…</Sign>
    <Cuit>20123456789</Cuit>
  </Auth>
  <PtoVta>1</PtoVta>
  <CbteTipo>6</CbteTipo>  <!-- 1=A · 6=B · 11=C -->
</FECompUltimoAutorizado>

Qué persistir de la respuesta

  • Resultado — A aprobado / R rechazado / con observaciones
  • CAE + CAEFchVto (yyyyMMdd)
  • CbteNro, mensajes de error/obs
Sin CondicionIVAReceptorId el CAE puede rechazarse (RG 5616). Catálogo: método FEParamGetCondicionIvaReceptor.

Envolver esto en tu propia API REST

Patrón recomendado (el de stock-local):

  1. GET /status — ¿hay cert/key/env?
  2. POST /invoices/{saleId} — adentro: ticket WSAA → último → FECAESolicitar → guardar
  3. GET /invoices/{saleId} — leer CAE ya pedido

Contrato listo para Postman: arca-api.html · colección JSON.

Variables típicas en tu servidor: ARCA_ENABLED, ARCA_ENV (HOMO/PROD), ARCA_CUIT, ARCA_CERT_PATH, ARCA_KEY_PATH, ARCA_PTO_VTA.
